# Echo 表情资源与 AI 机器人能力指南

本文保留资源清单格式、同步脚本的开发参考和 AI 能力对照。普通用户通过管理页面添加资源，不再需要编辑这些清单；当前操作步骤以[表情库管理指南](sticker-library-management.md)为准。

## 1. 两套表情库的区别

| 项目 | Echo 内置表情 | 机器人专属表情 |
|---|---|---|
| 谁使用 | 当前小队成员在聊天输入框手动选择 | 指定 AI 机器人通过 `sticker.send` 能力选择并发送 |
| 资源根目录 | 系统/个人库由管理页面上传；旧 `expression-packs/<serverId>/` 仅作导入 | 所有机器人继承系统图库，创建者可上传专属表情；旧 `ai-sticker-packs/<agentId>/` 仅作导入 |
| 清单绑定 | 单小队部署下的系统默认/上传者个人范围 | 系统默认范围或数据库中的机器人 ID，例如 `agent-whale` |
| 分组 | `emoji` 或 `sticker` 分组 | 情绪分组，例如 `cute`、`happy` |
| 同步命令 | `docker compose exec -T api node /app/scripts/sync-expression-packs.js` | `docker compose exec -T api node /app/scripts/sync-ai-sticker-packs.js` |

用户表情库与机器人图库彼此独立。把图片放入个人库不会自动给机器人使用，机器人图库也不会出现在用户表情选择器。历史消息引用的图片会保留，即使资源下架。

## 2. 旧版/批量导入：配置用户内置表情清单

### 2.1 准备目录

在 Echo 项目根目录，为目标小队创建或编辑：

```text
expression-packs/
└── server-squad/
    ├── manifest.json
    ├── cute-wave.webp
    └── game-win.png
```

目录名必须与清单中的 `serverId` 相同。示例 `expression-packs/server-squad/manifest.json`：

```json
{
  "serverId": "server-squad",
  "groups": [
    {
      "key": "cute",
      "kind": "sticker",
      "name": "卖萌",
      "items": [
        { "key": "cute-wave", "name": "挥手卖萌", "file": "cute-wave.webp" }
      ]
    },
    {
      "key": "game",
      "kind": "sticker",
      "name": "游戏开黑",
      "items": [
        { "key": "game-win", "name": "赢了", "file": "game-win.png" }
      ]
    },
    {
      "key": "custom-emoji",
      "kind": "emoji",
      "name": "自定义 Emoji",
      "items": [
        { "key": "gg", "name": "GG", "file": "gg.webp" }
      ]
    }
  ]
}
```

把每个 `file` 对应的图片放在同一个小队目录。`kind` 只能是 `sticker` 或 `emoji`。Emoji 单张最大 256 KiB、名称最多 32 字；贴图最大 2 MiB、名称最多 40 字。支持 PNG、JPEG、GIF、WebP。分组名称最多 32 字，`key` 只用英文字母、数字、下划线和连字符。

### 2.2 同步到本地或 VPS

先确认 Compose 项目目录下的资源目录已经挂载到 API 容器（项目默认挂载为只读）。在项目目录执行：

```bash
docker compose exec -T api node /app/scripts/sync-expression-packs.js
```

脚本会验证清单、小队是否存在、图片编码和大小，再把图片复制进 uploads 持久卷并更新数据库。成功后刷新 Echo 页面，在表情选择器中检查分组和图片。

如果刚新增了小队，先在 Echo 中创建小队，再同步。删除清单中的条目会使其不再出现在选择器中；已发送消息仍保留历史图片。

## 3. 旧版/批量导入：配置 AI 机器人表情清单

### 3.1 确认机器人 ID

资源目录名必须是机器人 ID，而不是显示名称。可在机器人管理页面查看；示例机器人为 `agent-whale`。机器人必须已经创建，且属于对应的小队。

### 3.2 准备目录和清单

```text
ai-sticker-packs/
└── agent-whale/
    ├── manifest.json
    ├── 001-shy.webp
    └── 002-pout.webp
```

`ai-sticker-packs/agent-whale/manifest.json` 示例：

```json
{
  "agentId": "agent-whale",
  "groups": [
    {
      "key": "cute",
      "emotion": "cute",
      "name": "卖萌",
      "items": [
        {
          "key": "shy",
          "name": "害羞卖萌",
          "description": "害羞、撒娇或想讨个抱抱时使用。不要用于严肃求助。",
          "file": "001-shy.webp"
        },
        {
          "key": "pout",
          "name": "鼓脸卖萌",
          "description": "轻松斗嘴、假装生气或撒娇时使用。",
          "file": "002-pout.webp"
        }
      ]
    }
  ]
}
```

把图片放在该机器人目录，并确保 `agentId` 与目录名一致。每张图片最大 2 MiB，支持 PNG、JPEG、GIF、WebP；名称最多 40 字，描述最多 240 字。分组 `key` 和 `emotion` 使用英文字母、数字、下划线或连字符，显示名称可以中文。

描述应写清楚“什么情境适合用”，这部分会作为选图提示交给模型。建议先少量按情绪分组，图片含义明显且避免多个几乎相同的候选，便于机器人稳定选图。

### 3.3 同步并启用能力

在含 `docker-compose.yml` 的部署目录运行：

```bash
docker compose exec -T api node /app/scripts/sync-ai-sticker-packs.js
```

脚本输出类似：

```text
Synced agent-whale: 1 emotion groups, 2 stickers
Done. 2 bot sticker assets processed.
```

随后在 Echo 的机器人管理页确认：

1. 鲸鱼娘已启用，且已安装到要测试的文字频道。
2. 在“能力/工具”中开启“发表情包（`sticker.send`）”。
3. 提供方 API Key 已配置，机器人能正常回复。
4. 通过 @机器人或私聊明确测试，例如：“用一张卖萌表情回应我”。

机器人图库只会在一次合法的回复中被模型选用，通常作为独立图片消息跟在文字回复之后；它不会凭空主动发消息，也不保证每次都会选图。不要把“消息里上传的任意图片”当作可供机器人发出的图库资源。

### 3.4 更新、删除和服务器部署

- 替换图片或改描述：更新 manifest/图片后再次运行同步命令。
- 从 manifest 移除一项：再次同步后，该条目对后续机器人回复停用；历史消息图片继续可读。
- 新增 pack 文件夹：先确保目标 agent 已存在，再同步。
- 本地测试成功后部署 VPS：把资源目录和 manifest 一并纳入部署版本，再按项目部署流程更新 VPS；在 VPS 的 `/opt/echo` 部署目录再次运行同一个 `docker compose exec ...` 同步命令。只在 Windows 本机同步不会改变 VPS。
- API 容器将资源源目录只读挂载；同步后的图片放入 uploads 持久卷。不要直接改容器内文件，也不要清理 uploads 卷来删除单个资源。
- 仅个人测试的图片不要误提交到公开仓库。若要随项目部署，将清单和已确认可分发的图片一起纳入版本控制；否则需通过受控方式复制到 VPS 资源目录后再同步。

## 4. Echo 与 dafeiyu-bot 的机器人能力对照

对照依据：本地 Echo 当前实现，以及 `dafeiyu-bot` 当前公开 README、操作指南和表情库说明（访问日期 2026-10-29）。对方项目规模和用途明显更广，功能清单不等于每项都适用于 Echo，也不代表我们已实测其所有能力。

| 能力 | Echo 当前实现 | dafeiyu-bot 项目公开能力 | 对 Echo 的启发 |
|---|---|---|---|
| 产品集成 | 机器人是 Echo 小队成员；可安装到文字频道，并支持机器人私聊 | 主要通过 QQ / OneBot 桥接，另有本机控制面板和实验中的其他社交平台 | 继续利用 Echo 原生消息、成员、频道和权限，不引入 QQ 适配层 |
| 人设 | 每个 agent 可配置名称、描述、人设、模型参数；修改有人设版本记录 | 多种内置性格、自定义角色 prompt，并可按群/好友单独设置性格 | 增加人设模板、按频道覆盖与版本预览；沿用当前 agent 单体设置作为默认 |
| 触发 | 私聊发送即回复；频道按安装配置触发，支持 @、回复等模式 | 好友/群白名单、真实 @，可按 N 条普通群消息评估是否加入话题 | 先增加可控的“每 N 条评估一次是否接话”，需冷却、每日上限和可关闭开关 |
| 短期上下文 | 当前按会话读取最近约 20 条消息；频道上下文从最近消息构造 | 短期上下文和历史整理，并关注引用还原、主人接话取消待发送回复 | Echo 应先做可配置上下文窗口和摘要压缩，避免长聊断片；不要直接把 QQ 所有逻辑照搬 |
| 长期记忆 | 尚无机器人可查询/编辑的持久长期记忆机制 | 按会话整理记忆、检索、纠正和删除；把角色、主人、好友分开处理 | 高优先级：以用户/频道分区，提供查看、纠正、删除和关闭记忆；默认不记录敏感内容 |
| 图片理解 | `image.read` 工具可分析被提及或回复消息中的图片；配置受视觉模型支持约束 | 图片/GIF 抽帧观察；公开文档称有限帧，不是完整视频理解 | 扩大到“引用的历史图片”、多图限额和 GIF 抽帧；明确图片进入第三方视觉模型前的提示 |
| 联网搜索 | 可选 `web.search`，DeepSeek Search；回复附来源 | 搜索与图片搜索/插画搜索、多来源回退 | Echo 的基础搜索足够；可改善来源质量、失败降级和引用展示，不必堆独立搜索命令 |
| 表情包 | 系统机器人图库由所有 bot 继承；每个 bot 可有专属补充，按模型工具选择并作为独立消息发送 | 本地图库、按语境/情绪/关键词配图、冷却与去重；图库导入保留来源/许可元数据 | 增加机器人专属的触发条件、概率/冷却、去重和来源字段；与用户表情库继续隔离 |
| 其他工具 | 当前内置工具为图片理解、联网搜索、机器人表情发送；管理员可逐项授权 | 还有生图、搜图、定时分享、社交平台浏览等多类工具 | 采用能力目录 + 明确授权的方式逐项扩展，暂不做任意代码插件或不受控外部动作 |
| 运行保护 | 有频道安装开关、工具授权、2 秒私聊节流、审计事件和生成异常回执 | 有白名单、调用/发送额度、冷却、图片去重、定时任务限制等 | 统一加入用户/频道/机器人级预算、队列上限、重复事件幂等、请求超时与可观测性 |

### 推荐的 Echo 下一步

1. **记忆 v1**：短期上下文可配置；长期记忆按“每个用户 × 每个频道/私聊”隔离，支持查看、修改、删除和关闭；摘要生成异步化并保留原消息。
2. **机器人回复质量**：增加人设模板和频道级性格覆盖；展示最近触发/工具调用/失败原因，便于朋友测试时定位问题。
3. **群聊自然接话**：可选每 N 条消息评估一次，默认关闭；加随机冷却、每日限额、人工新消息取消排队回复，防止刷屏和抢话。
4. **工具运行治理**：每次模型循环限定工具调用数量、超时和输出大小；记录耗时、预算和错误类别；搜索/图片结果作为不可信输入处理。
5. **表情策略**：在现有资源清单基础上增加可调触发方式、每会话冷却和最近发送去重，并让管理员预览描述与图片。

近期不建议移植：QQ/OneBot 连接、社交平台自动浏览/发帖、插画社区发布链路、复杂插件市场。这些是对方平台适配或产品方向，不是 Echo 几个朋友开黑聊天的核心需求。

## 5. 运维检查

查看同步是否成功：

```bash
docker compose logs --tail=100 api
docker compose exec -T api node /app/scripts/sync-expression-packs.js
docker compose exec -T api node /app/scripts/sync-ai-sticker-packs.js
```

同步脚本直接连接数据库，不依赖重建镜像。若文件已更新但页面/机器人仍使用旧图，确认当前目录的 manifest 与文件已更新，再重新运行相应同步脚本，并刷新页面或重新发起一轮机器人对话。
